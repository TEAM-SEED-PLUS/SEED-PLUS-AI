# [F] 소비 의도 실측 하이브리드 데이터 연동 조사

- 조사일: 2026-08-23 (KST)
- 범위: 서울시 상권분석서비스 추정매출(자치구)과 OA-22385 실시간 상권현황데이터의 라이브 응답 검증
- 상태: **조사·프로브 완료 / 운영 산식 미변경**

## 1. 결론

권고안은 **B안: 분기 추정매출을 자치구 소비의도 주 기준선으로 두고, TourAPI는 관광 소비 특성 보정으로 축소 유지**하는 것이다. OA-22385는 자치구 총량이 아니라 82개 주요 장소의 현재 소비 상황이므로, 장소-자치구 매핑과 커버리지 정책이 확정된 곳에서만 실시간 보정 후보로 써야 한다. OA-21285 유동인구는 소비 자체가 아니라 유입·소비 기회의 별도 신호로 유지한다.

이번 단계에서는 가중치, 구간, cap, 결측 시 허용 경과 분기를 확정하지 않는다. 특히 OA-22385를 자치구 합계로 오인하거나, 공개 API에 없는 전주·최근 28일 증감률을 생성해서는 안 된다.

## 2. 현재 운영 `spending_intent` 산식

```text
spending_intent = clamp(0, 100,
    24
    + content_spending_bonus
    + footfall_spending_bonus
    + weather_spending_bonus
    + special_day_spending_bonus
    + tourapi_spending_bonus
)
```

| 구성 | 현재 계산 | 상한/범위 |
|---|---|---:|
| base | 고정값 | 24 |
| content | 공연×4.5 + premium tag×2.6 + 행사×2.2 + family tag×1.4 | 24 |
| footfall | OA-21285 평균 인구 percentile을 adapter가 bonus로 공급; S-DoT fallback은 `log10(visitor_avg+1)×6.5` | 10 |
| weather | 맑음 +6, 구름 일부 +3, 실내 콘텐츠가 있는 비 +4, 12~24℃ +4, 폭풍 -6 등 | 명시적 단일 cap 없음 |
| special day | 공휴일×6 + 기타 특일×1.5 | 10 |
| TourAPI | `spending 0.50 + food 0.35 + age diversity 0.15` 지수의 0~100 값을 bonus로 환산 | 10 |

실패 원천은 그 원천 bonus만 제외하고 base를 유지한다. 본 조사에서 위 코드와 설정은 변경하지 않았다.

## 4. OA-22385 실시간 소비 신호

### 4.1 출처, 공간 단위와 스키마

- 공식 데이터셋: `서울시 실시간 상권현황데이터`, OA-22385
- 라이브 OpenAPI 서비스명: `citydata_cmrcl`
- 원천: 신한카드 내국인 소비 기반 가공 데이터
- 갱신: 약 10분
- 공간 단위: **주요 장소 `AREA_CD` 한 곳**. 응답에 자치구 필드는 없다.
- 상권 데이터 제공 범위: 주요 장소 중 82곳

상위 응답 필드는 `list_total_count`, `AREA_CD`, `AREA_NM`, `RESULT`, `LIVE_CMRCL_STTS`다. `LIVE_CMRCL_STTS`의 정확한 필드는 다음과 같다.

```text
AREA_CMRCL_LVL
AREA_SH_PAYMENT_CNT
AREA_SH_PAYMENT_AMT_MIN, AREA_SH_PAYMENT_AMT_MAX
CMRCL_RSB[]:
  RSB_LRG_CTGR, RSB_MID_CTGR, RSB_PAYMENT_LVL,
```

`AREA_CMRCL_LVL`은 `한산한/보통/바쁜/분주한` 4단계이며, 과거 4주 동일 장소·업종의 같은 요일·같은 시각 전후 30분 평균을 바탕으로 한 수준이다. 공개 API 응답에는 웹 화면에 보이는 전시간·전주·최근 28일 대비 수치 필드가 없다. 따라서 그 변화율을 추정하거나 이름만 같은 필드를 만들어 사용하지 않는다.

금액은 최소·최대 범위이고 특정 카드사의 내국인 소비 기반 가공값이다. 서울 전체 또는 장소의 정확한 카드매출 총액으로 표현해서는 안 된다.

## 5. 공간 매핑과 커버리지

| 원천 | 원천 공간 | 자치구 필드 | 현재 연결 방법 | 커버리지 의미 |
|---|---|---|---|---|
| 추정매출 | 자치구 | `SIGNGU_CD/NM` 있음 | 직접 연결 | 25개 구 기준선 |
| OA-22385 | 주요 장소 | 없음 | 기존 OA geometry 후보 파일로 단일 유효 자치구 매핑 | 82개 장소만 관측 |

기존 `data/oa21285/reference/mapping_candidates_20260402.json`을 재사용할 수 있지만, 경계 횡단 장소의 단일 귀속 정책이 먼저 필요하다. 같은 구의 여러 장소를 단순 합산하거나, 대표 장소 하나를 그 구 전체로 간주하면 안 된다. 제품 입력이 자치구인지 사용자 주변 장소인지도 실시간 보정 설계 전에 확정해야 한다.

## 6. TourAPI·OA-21285와의 중복

- **TourAPI 대 추정매출:** TourAPI는 관광 소비의 상대적 특성, 추정매출은 자치구 전체 소비 기준선이다. 둘 모두에 큰 독립 bonus를 주면 소비 수준을 중복 반영한다. 추정매출을 주 기준선으로 두고 TourAPI는 관광 편중·구성 보정으로 축소하는 B안을 권고한다.
- **OA-21285 대 OA-22385:** 유동인구는 소비 기회/유입, OA-22385는 관측 장소의 현재 소비다. 의미상 분리되지만 현실에서는 상관되므로 공통 cap 또는 상호작용 규칙이 필요하다. OA-21285를 삭제할 근거는 없으며, 실시간 소비 신호가 있는 곳에서도 유입 맥락으로 유지한다.
- **콘텐츠·날씨·특일:** 당일 의도 변화 신호이므로 분기 기준선과 역할이 다르다. 다만 최종 cap 없이 누적하면 강한 신호일에 포화될 수 있어 후속 산식 설계에서 함께 검토한다.

## 7. 권고 하이브리드 구조

```text
자치구 분기 추정매출 기준선 (주 실측 baseline)
  + TourAPI 관광 소비 구성 보정 (축소 후보)
  + 콘텐츠/날씨/특일 당일 의도 신호
  + OA-21285 유입·소비 기회 신호
  + OA-22385 장소 단위 실시간 소비 보정 (매핑·커버리지 충족 시만)
  -> 기존 0~100 spending_intent 체계
```

다음 정책 결정 전에는 운영 연결을 보류한다.

1. 기준선 원지표: 총액, 업종 정합 점포당 매출, 또는 혼합 지표
2. 25개 구 percentile/구간과 bonus·penalty 방향 및 cap
3. TourAPI의 새 역할과 축소 폭
4. OA-22385 장소 여러 개의 결합법, 경계 장소, 미커버 자치구 처리
5. 실시간 level의 ordinal 수치화와 OA-21285와의 공통 cap
6. 기준선 허용 경과 분기 및 방법론 변경 시 재기준화

## 8. 저장·갱신·fallback 설계안

```text
data/consumption/
  estimated_sales/raw/{quarter}/page_{start}_{end}.json
  estimated_sales/normalized/{quarter}.json
  estimated_sales/manifest.json
  realtime_commerce/latest/{area_cd}.json
  realtime_commerce/history/{yyyy-mm-dd}/{hhmm}/{area_cd}.json
  realtime_commerce/manifest.json
```

- 분기 기준선: 전체 페이지 수집 → 응답/중복 검증 → client-side 분기 필터 → 원본 불변 저장 → 정규화 결과를 별도 저장한다.
- 실시간: 10분 TTL의 latest와 조사·품질 검증용 제한된 history를 분리한다. 개인정보가 아닌 집계 응답만 저장한다.
- 모든 스냅샷에 `source_status`, 요청/원천 시각, 원천 분기 또는 `CMRCL_TIME`, API 호출 수, row 수, grain 중복 수, 매핑 버전을 둔다.
- 기준선 실패: 마지막 성공 분기를 후보 fallback으로 사용하되 허용 경과 분기는 정책 확정 전 미정이다. 성공 이력이 없으면 기준선 bonus를 제외한다.
- 실시간 실패/미커버: 분기 기준선만 사용하며 다른 bonus를 재비례 확대하지 않는다.
- 둘 다 실패: 기존 base와 기존 콘텐츠·유동·날씨·특일·TourAPI만 유지하고 `data_insufficient`를 노출한다.
- `no_data`, `failed`, `malformed`, `partial`, `fallback`을 구분하며 실패를 0매출로 저장하지 않는다.

## 9. 구현·검증 범위

조사 전용 `consumption_data_probe.py`를 추가했다. 추정매출 pagination과 grain 중복 검출, OA-22385의 비표준 상위 응답 파싱, API 오류/무자료/비정상 응답 구분, 예외 메시지의 API key 비노출을 포함한다. 운영 수집기와 점수 계산에는 import하거나 연결하지 않았다.

테스트 범위는 정상, pagination, 중복 grain, `no_data`, HTTP/API 실패, malformed, 실시간 정상·무자료·malformed, 반환값 API key 비노출이다.
